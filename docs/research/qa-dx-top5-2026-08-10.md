# QA — DX top-5 integration wave (2026-08-10)

Under test: the integration branch merging the four DX slices — the
mock actions backend, broker-transparent clients, version surfacing +
optional bearer-token auth, and `POST /v0/runs` + YAML run-spec +
`manzanas run` + the MCP `run` tool.

**Verdict: ship-ready AFTER this PR** — the slices compose correctly with
two real integration bugs found and fixed here:

1. The broker had no `/v0/runs` route, so the composition "`manzanas
   run` / MCP `run` pointed only at the broker" (the headline of the
   clients x runs slices) failed with `not_found: unknown route`. Fixed
   by federating runs through the broker (placement + proxy + sync
   polling), with unit tests and doc updates.
2. The run engine's boot stage returned as soon as `simctl boot` was
   accepted, so on real hardware the `launch` stage raced a still-Booting
   sim (`Unable to lookup in current state: Booting`, reproduced on an
   Apple Silicon Mac host under load). Fixed by having the boot stage
   poll until the target actually reports Booted.

## Bug 1 (fixed in this PR)

**`POST /v0/runs` against the broker → 404 `unknown route`.**
`internal/server` registers `/v0/runs` on the daemon, but
`internal/broker.(*Broker).Handler` never did — every run frontend (CLI
`manzanas run`, MCP `run`, raw HTTP) failed when pointed at a broker,
while `docs/runs.md` + the broker-transparent-clients posture ("clients
only need the broker address") implied it should work. Runs are the one
target-scoped surface that *cannot* use the lease-follow fallback,
because the run *is* the thing that acquires the lease — the broker must
place it.

Fix (`internal/broker/runs.go`):
```text
POST /v0/runs      placement labels = spec labels + runtime/device_type slugs
                   (host labels pin; pinned udid filters candidates);
                   ranked like lease acquire (warm-first); submitted
                   async to the winner; sync clients served by broker-side
                   polling until terminal (budget + margin bound).
                   400/501 from the daemon forwarded verbatim;
                   503 overloaded tries the next candidate.
GET  /v0/runs      federated union, newest first, annotated host/host_addr
GET  /v0/runs/{id} routed to the owning daemon (fallback: ask each up host)
```
`proto.Run` gains additive `host`/`host_addr` (mirroring `Lease`). Tests:
`internal/broker/runs_test.go` (sync placement, async + host-pin, error
paths). Docs: PROTOCOL.md §9, docs/broker.md, docs/runs.md.

## Bug 2 (fixed in this PR)

**Run boot stage races app launch on real sims.** The first
real-hardware run failed:
```text
error: internal: launch: simctl launch failed: exit status 149:
Unable to lookup in current state: Booting
```
The journal shows `targets.boot ok` and `launch_app error` at the same
second: `bootTargetWait` waits for *capacity gates*, and
`SimctlRegistry.Boot` returns when `simctl boot` is accepted — nothing
waits for the sim to reach Booted. Mocks flip to Booted synchronously
(why the slice's own smoke tests passed) and interactive CLI users poll
`manzanas targets` by hand; the one-call run engine skipped that step.
Fix: `waitTargetBooted` in the boot stage (polls registry Health until
Booted, 3 min bound). Re-run of the identical spec passed 4/4 steps.

## Ship-readiness

The integration branch as merged is NOT ship-ready on its own: the
broker run path 404s and real-hardware runs race the boot. With this
PR's two fixes (both re-verified end-to-end on mocks and real hardware),
the wave composes correctly and is ship-ready.
